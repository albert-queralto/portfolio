# Internationalization (en / ca / es / de)

The portfolio uses Astro's built-in i18n routing with English as the unprefixed default locale.

## URL structure

| Language | Home | Blog | Project example |
| --- | --- | --- | --- |
| English | `/` | `/blog/` | `/projects/payrithm/` |
| Català | `/ca/` | `/ca/blog/` | `/ca/projects/payrithm/` |
| Español | `/es/` | `/es/blog/` | `/es/projects/payrithm/` |
| Deutsch | `/de/` | `/de/blog/` | `/de/projects/payrithm/` |

English URLs are unchanged so existing links and search indexing continue to work.

## Main files

- `astro.config.mjs` — locales and default-locale routing.
- `src/i18n/config.ts` — supported locale codes and display names.
- `src/i18n/translations.ts` — shared interface copy.
- `src/i18n/experience.ts` — localized career timeline.
- `src/i18n/flagships.ts` — localized Payrithm/TenderWise homepage copy.
- `src/i18n/utils.ts` — locale and URL helpers.
- `src/i18n/content.ts` — translated-content selection and fallback logic.
- `src/components/LanguageSwitcher.astro` — language selector.
- `src/components/pages/*` — shared page implementations used by all locale routes.
- `scripts/check-i18n.mjs` — structural validation.

## Astro configuration

The site uses:

```js
i18n: {
  defaultLocale: "en",
  locales: ["en", "ca", "es", "de"],
  routing: {
    prefixDefaultLocale: false,
  },
},
```

Do not create `/en/` URLs unless you intentionally change `prefixDefaultLocale`.

## Static interface translations

Shared UI text lives in:

```text
src/i18n/translations.ts
```

When adding a new label to a component, add the same key to all four locale objects.

Example:

```ts
nav: {
  home: "Home",
  projects: "Projects",
}
```

Components obtain the active locale from the URL:

```astro
---
import { getLocale, getMessages } from "@/i18n/utils";

const locale = getLocale(Astro.currentLocale);
const t = getMessages(locale);
---

<h1>{t.projects.title}</h1>
```

## Localized internal links

Never hard-code `/blog/` or `/projects/.../` when the link should remain in the visitor's selected language.

Use:

```ts
localizePath(locale, "/blog/")
```

Examples:

```ts
localizePath("en", "/blog/") // /blog/
localizePath("ca", "/blog/") // /ca/blog/
localizePath("es", "/projects/payrithm/") // /es/projects/payrithm/
```

The language switcher removes the current locale prefix and rebuilds the same route in the selected language.

## Blog content translations

Existing blog posts remain valid without any changes. Their schema defaults to:

```yaml
lang: en
```

To create a Catalan translation, add a second Markdown file. A recommended structure is:

```text
src/content/blog/
├── payrithm.md
├── tenderwise.md
├── ca/
│   ├── payrithm.md
│   └── tenderwise.md
├── es/
│   └── ...
└── de/
    └── ...
```

The translated file must identify its language and the shared translation key:

```yaml
---
title: "Validació temporal per predir pagaments tardans"
description: "..."
date: 2026-09-29
publishAt: 2026-09-29T08:00:00+02:00
lang: ca
translationKey: temporal-validation-late-payment-prediction
tags: ["Machine Learning", "Sèries temporals"]
draft: false
cover: "/og/temporal-validation-late-payment-prediction.png"
---
```

The English source can optionally declare the same key explicitly:

```yaml
lang: en
translationKey: temporal-validation-late-payment-prediction
```

For existing English files, `translationKey` is optional. Their current content ID is used automatically.

## Project translations

Projects use the same mechanism:

```text
src/content/projects/payrithm.md
src/content/projects/ca/payrithm.md
src/content/projects/es/payrithm.md
src/content/projects/de/payrithm.md
```

Localized project frontmatter:

```yaml
lang: ca
translationKey: payrithm
```

Keep the internal `status` and `category` codes in English because they are data keys used by filtering:

```yaml
status: "Deployed"
category: "Machine Learning"
```

The UI translates those values for the visitor.

## Fallback behavior

You do not need to translate every long-form page immediately.

When a visitor selects Catalan, Spanish, or German and a translated article/project does not exist:

1. the localized route still works;
2. navigation and page controls remain in the selected language;
3. the English source content is displayed with a clear fallback notice;
4. the fallback page receives `noindex`;
5. its canonical URL points to the real English source;
6. `hreflang` only advertises languages for which real content exists.

This prevents the English body from being indexed four times as duplicate translated content.

Once a real translation is added, the same URL automatically becomes an indexable translated page on the next build.

## Canonical and hreflang behavior

General translated pages such as the home and blog index are self-canonical:

```text
/                 -> canonical /
/ca/              -> canonical /ca/
/es/blog/         -> canonical /es/blog/
/de/blog/         -> canonical /de/blog/
```

They also emit alternate links for `en`, `ca`, `es`, and `de`, plus `x-default` pointing to English.

Long-form content emits alternates only for translations that actually exist.

## `publishAt` and scheduled publishing

The blog schema keeps:

```yaml
publishAt: 2026-09-29T08:00:00+02:00
```

Future posts are excluded from:

- blog listings;
- generated article content selection;
- RSS;
- sitemap.

The Option-B scheduler created for the VPS scans the blog directory recursively, so locale subfolders remain compatible with it.

If all translations share the same publication timestamp:

```yaml
# English
publishAt: 2026-09-29T08:00:00+02:00

# Català
publishAt: 2026-09-29T08:00:00+02:00

# Español
publishAt: 2026-09-29T08:00:00+02:00

# Deutsch
publishAt: 2026-09-29T08:00:00+02:00
```

one rebuild publishes all four versions.

Translations can also be scheduled independently.

## RSS

`/rss.xml` remains the English/default feed. Only published English posts are included.

This avoids mixing languages in one feed. Separate locale feeds can be added later if desired.

## Sitemap

The sitemap includes:

- all four home pages;
- all four blog indexes;
- English long-form content;
- any real translated article/project files.

Fallback/noindex article and project routes are deliberately omitted.

## Add a new static UI string

1. Add the key to `messages.en`.
2. Add the Catalan translation to `messages.ca`.
3. Add the Spanish translation to `messages.es`.
4. Add the German translation to `messages.de`.
5. Read it from the component through `getMessages()`.
6. Run the checks below.

## Validation

Run:

```bash
npm run i18n:check
npm run check
npm run build
npm run format:check
```

The normal `npm run check` includes the i18n structural check.

After a successful build, inspect representative pages:

```text
/
/ca/
/es/
/de/

/blog/
/ca/blog/
/es/blog/
/de/blog/

/projects/payrithm/
/ca/projects/payrithm/

/blog/payrithm/
/ca/blog/payrithm/
```

Until a Catalan Payrithm project/article translation exists, the `/ca/...` long-form routes should show the English fallback notice and include `noindex`.

## SEO checks after deployment

For each language verify:

- `<html lang="...">` is correct;
- canonical URL matches the page when it is genuinely translated;
- `hreflang` links point to real translations;
- fallback long-form pages are `noindex` and canonical to the English source;
- Open Graph locale is `en_GB`, `ca_ES`, `es_ES`, or `de_DE`;
- structured-data `inLanguage` matches translated content.

## Adding another language later

To add another locale, for example French:

1. add `fr` to `src/i18n/config.ts`;
2. add it to `astro.config.mjs`;
3. add `messages.fr` and any translated static data;
4. create `src/pages/fr/` route wrappers matching the existing locale folders;
5. add the locale to the content schema enums;
6. update the content-key prefix regex in `src/i18n/utils.ts`;
7. update `scripts/check-i18n.mjs`;
8. run the full build and SEO checks.
